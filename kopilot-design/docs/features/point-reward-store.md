# 포인트 리워드 상점

## 1. 배경

챌린지 성공으로 포인트를 받지만 사용할 곳이 없어 보상 경험이 적립에서 끝난다. 포인트를 일상적인 모바일 교환권으로 바꿀 수 있게 해 `절약 행동 → 포인트 획득 → 작은 보상 → 다음 챌린지 참여`의 반복 동기를 만든다.

## 2. 목표

- 마이 화면에서 현재 포인트와 사용처를 바로 이해한다.
- 적은 포인트로도 도달 가능한 상품을 먼저 보여준다.
- 구매 전후 잔액을 명확히 안내해 금융 서비스의 신뢰감을 유지한다.
- 실제 적립 포인트와 mock 상품 데이터로 전체 구매 흐름을 확인한다.

## 3. 사용자 흐름

1. 사용자가 하단 탭에서 `마이`로 이동한다.
2. 포인트 지갑에서 현재 잔액과 보유 기프티콘 수를 확인한다.
3. `포인트샵 가기` 버튼을 눌러 별도 `/point-shop` 화면으로 이동한다.
4. 전체, 카페, 편의점, 디저트, 문화 탭으로 상품을 탐색한다.
5. 상품을 선택해 보유 포인트, 사용 포인트, 구매 후 포인트를 확인한다.
6. 잔액이 충분하면 구매하고, 부족하면 필요한 추가 포인트를 확인한다.
7. 구매 완료 후 교환권 번호를 확인하거나 `내 기프티콘` 보관함으로 이동한다.
8. 상단 뒤로가기로 마이 화면에 복귀한다.

## 4. 포인트 원장과 Mock 정책

- 실제 적립 포인트: 챌린지 성공 시 갱신되는 DB `users.total_points`
- 조회 API: `GET /api/users/me/reward-points`
- 랭킹 점수 제외: `rankScore`에는 절약액 환산 점수가 포함되므로 구매에 사용할 수 없다.
- 사용 가능 포인트: `실제 적립 포인트 - mock 구매에 사용한 포인트`
- 환산 표기: `1P = 1원`
- 상품 카테고리: `cafe`, `convenience`, `dessert`, `culture`
- 상품 필드: `id`, `brand`, `name`, `points`, `category`, `emoji`, `color`, `badge`, `description`
- 구매 필드: `id`, `productId`, `purchasedAt`, `giftCode`
- 상품과 구매 목록은 mock이며 구매 목록만 로그인 사용자 식별자별 `localStorage`에 저장한다.
- 임의의 초기 포인트나 별도 잔액을 브라우저에 저장하지 않는다.
- 동일한 상품을 여러 번 구매할 수 있다.
- 잔액보다 비싼 상품은 상세를 확인할 수 있지만 구매 버튼을 비활성화한다.
- 상품과 포인트가 체험 데이터임을 화면 하단에 명시한다.

## 5. 상태와 예외 처리

| 상태 | 화면 처리 |
| --- | --- |
| 구매 가능 | 파란색 구매 CTA와 구매 후 잔액 표시 |
| 포인트 부족 | 부족 포인트 안내와 비활성 CTA |
| 구매 완료 | 완료 아이콘, 교환권 번호, 보관함 CTA |
| 보관함 비어 있음 | 첫 리워드 구매를 유도하는 빈 상태 |
| 포인트 API 조회 실패 | 상품 구매를 잠그고 다시 시도 CTA 제공 |
| 저장소 읽기 실패 | 빈 보관함으로 복구 |
| 저장소 쓰기 실패 | 현재 세션 상태는 유지 |

## 6. 실제 API 전환 시 고려사항

- 포인트 원장을 단일 진실 공급원으로 사용한다.
- 구매 요청에는 idempotency key를 포함해 중복 차감을 막는다.
- 포인트 차감과 제휴 교환권 발급 상태를 서버 트랜잭션으로 관리한다.
- 교환권 번호는 화면과 로그에서 마스킹하고 사용자 인증 후 조회한다.
- 품절, 가격 변경, 발급 실패, 부분 보상 정책을 별도로 정의한다.
